# AI-Assisted SOC Anomaly Detection

This stage follows **Python preprocessing** and reads `outputs/cleaned_all_logs.csv`. It does not replace the processing script or the simulated CSV files already in `data/`.

## Install and run (VS Code terminal)

From the root of your `ai-insider-threat` repository:

```powershell
python -m pip install -r requirements_detection.txt
python src/log_processing.py
python src/anomaly_detection.py
python -m unittest discover -s tests -v
```

If `outputs/cleaned_all_logs.csv` has already been generated successfully, the preprocessing step can be skipped. On some Windows systems, `py` may be used instead of `python`.

## Inputs

- `outputs/cleaned_all_logs.csv`: Unified and normalized security log events generated by the Python preprocessing layer.
- `data/`: Synthetic security logs covering authentication, file access, endpoint activity, privilege use, and HDR/human-risk events.

## Outputs

Running `src/anomaly_detection.py` generates:

| File | Purpose |
|---|---|
| `outputs/user_baselines.csv` | Per-user training login-hour statistics, known devices, download thresholds |
| `outputs/ml_daily_anomalies.csv` | Daily user behavior features and IsolationForest outlier result |
| `outputs/detection_event_results.csv` | Every event with explanation and risk score, including non-alerts |
| `outputs/detection_alerts.csv` | Only events with risk score >= 25 |
| `outputs/correlated_cases.csv` | Related alerts grouped by user within a 24-hour consecutive-event gap |
| `outputs/detection_test_report.txt` | Synthetic label-based evaluation and important limitations |

## Detection approach

1. **User baselines:** Train on the first *seven distinct dates* (Sept 14–22 in this supplied dataset) and evaluate later dates. Learn typical successful login hours and devices, and download counts. This split avoids future-event leakage.
2. **After-hours logins:** Mark logins before 07:00 or at/after 19:00, and deviations from typical per-user login hours.
3. **Failed-login patterns:** Detect three or more failed logins by one user within 30 minutes.
4. **New-device activity:** Compare successful-login devices against devices observed in the training period.
5. **Abnormal file access:** Detect bursts of downloads and after-hours downloads of sensitive-named files. This dataset contains no transferred-byte quantities, so we use download **counts**, not claimed byte volume.
6. **Privilege misuse:** Flag failed permission-change attempts, role lookups, and after-hours admin console actions.
7. **HDR signals:** Flag phishing-link clicks, warning bypasses, and suspicious credential submissions.
8. **Rule-based checks:** Transparent checks add evidence and weighted points. Suspicious endpoint processes are also included.
9. **Anomaly checks:** Statistical login-time baselines plus a real `scikit-learn` **IsolationForest** trained on numerical user-day features. ML is supplementary and cannot by itself manufacture an event-level alert.
10. **Event correlation:** Alert grouping by user and time window; no synthetic `incident_id` is used to form cases.
11. **Risk scoring:** Weighted, capped 0–100 per-event scores, then per-case severity based on the strongest event and diverse supporting signals. This is a demonstration scoring rubric, not a calibrated probability.
12. **Injected-event tests:** Run included `unittest` tests and review `detection_test_report.txt`.

## Expected output on the supplied unchanged dataset

- 453 events processed, across ten synthetic users
- 26 event alerts, representing all 26 deliberately injected suspicious events
- One correlated `m.chen` case spanning five log categories, with high risk

**Important:** This perfect result is specific to an intentionally designed toy dataset, and does **not** demonstrate production accuracy, false-positive control under real workloads, generalization, or privacy/security assurances. Normal training-period outliers can occur in the ML daily analysis, even when they do not become event alerts. A realistic evaluation needs independent cases, background noise, changed user patterns, baselines that update safely, and data from different scenarios.

## Data provenance and ground truth

The CSVs were synthetically generated with AI assistance. `label`, `incident_id`, `risk_signal`, `severity`, and `details` are **not used for detection decisions**. `label` and `incident_id` are used only for the final validation report. A test specifically changes those fields to check that alerts do not change. Do not remove this distinction when presenting the results.
